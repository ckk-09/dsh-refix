## 修复引擎设计要点

1. **计划推导**（F2）：`restart`（run-missing → run 原版本）/ `soft-reset`（host-method-error → stop→run 当前版本）/ `switch`（模型指定 `targetPackageId` 候选修复版本，携带 fallback=当前版本）。mode 按 runner 校验规则现算：`current===target||无current → 'run'，否则 'update'`。
2. **观察窗判定无竞态**：窗口基线取"修复起点"的报告数；激活瞬间的事件巡检探针可能先于 `run()` 返回落册，任何更晚的截取点都会漏判。回退判定同理——基线先于回退 `run()` 调用截取（快照先于激活 ⇒ 激活探针的报告只可能更晚落册，结构性无竞态）。
3. **同步 diff 与异步探针分离**：巡检的 inventory diff 同步完成（事件触发当拍生效），health 探针异步发射并收集 promise（`drain`）；只有观察窗判定才 `await drain`。
4. **B4 审批门**：客户端半区 `run()` 返回 `awaiting-approval` → 修复记录该结果并返回，工具内绝不等待/重试（与 tool-cordis 官方 prompt 约定一致）。
5. **互斥与抑制**：修复期间 `repairing` 互斥；`suppressRunMissing` 抑制修复自身 stop/run 引起的 retract 误报（soft-reset 的 stop 会被误判为 run 消失）。
6. **知识库原料**：每次修复记录 `{id, symptom, plan, observeMs, outcome, result}` 入 `repairs`——P3 直接复用为历史方案。

## 踩坑记录（本轮 3 个，全部根因修复）

1. **异步探针阻塞 diff**（v3 初版把探针 await 内联进巡检）：retract 事件巡检在探针 await 处挂起 → stop() 先返回 → 测试先调 repair → 症状后落册 → `symptom:'none'` 拒修。修复：diff 同步/探针异步分离 + drain 机制。
2. **观察窗漏判**：`before` 截取点晚于激活瞬间落册的探针报告 → 坏版本被判 clean。修复：窗口基线提前到修复起点（两次迭代：先挪到 run 返回后仍踩中微任务竞态，最终改为"快照先于 run 调用"的结构性无竞态方案）。
3. **summary 丢字段**：工具返回手工挑字段漏掉 `rollback`，测试拿不到回退证据。修复：整结果展开。
