## 一、结论更正的裁决（P0，源码核定）

复检指出 P3R2 的审批机制表述有错，要求更正。逐行核验 run() 主体（宿主 L255-312）后的裁决是**双方各对一半**：

| 论点 | 裁决 | 依据 |
|---|---|---|
| 复检："startFresh 在 client-pending 之前就 plugin.run = run → 审批期间 run 已建立" | ❌ 不成立 | startFresh 的内部顺序（L856→L869-871）属实，但它运行在**批准之后**；`requiresApproval` 时 run() 在 **L301 直接 return**（startHost 从未执行）→ 审批 pending 期间 `plugin.run` 未建立。p2 的 `activeRun: null` 断言通过是实证 |
| 复检："真因是 resolution 缺 pluginRunId" | ❌ 不成立 | p3r2 首测**已传** `pluginRunId: r.pluginRunId`；真因是 L420 闸门比对 `plugin.run.pluginRunId`（undefined）必然失败 |
| 复检："拒绝分支不比对 runId（L421-422）→ 拒绝能过、批准过不去" | ✅ 正确 | 这补全了现象解释的另一半 |
| 复检："通道 B（resolveRequestRun ok:true）真实存在" | ✅ 正确（阶段限定） | 适用于**批准激活后的 client-pending 阶段**（plugin.run 已建，runId 闸门可过）——P3R3 实测该阶段调用 `accepted: true`（宿主对已提交激活的二次回执幂等） |

**最终表述**（已改写 P3R2.md item 1 + p3r2.ac.mts 注释）：审批两条合法通道——**A** `runHostHalf(requestId)`（批准驱动）；**B** `resolveRequestRun(ok:true, pluginRunId)`（client-pending attach 回执）。复检建议的通道 B 断言已补（p3r3.ac.mts：runHostHalf 批准 → 通道 B 回执 → 断言激活状态一致，accepted 值留档）。

**方法论认领**：复检指出这与上轮 V-11 是同一错误模式（"我没实现/payload 少字段"当成"平台必然"）——成立，已留档。本轮的裁决同样坚持了"回源码核"：复检的更正本身也有一半经不起源码检验，双向核验才是标准。

## 二、P-1 过滤巡检失盲（P1）— ✅ 修复

`patrol` 无条件重建 lastSeen 后才按 onlyPid 过滤 → 被过滤插件的状态跃迁被消费却不判定。修复（≤3 行精神）：**检测与基线推进永远全量，过滤只作用于返回视图**；探针仍只打目标（保留 O-7 的跨端调用节省）。

**可测差异断言**（v6 会挂、v7 过）：`reportRenderFailure`（无事件伴随）后过滤巡检他插件 → v7 下该症状**照常落册**（日志实证：`新增症状 1 条（过滤视图返回 0 条）`）。

## 四、实现中的新发现

1. **宿主取消契约的两种形态**：signal abort 时宿主 ToolRuntime 可能直接中断调用抛 `tool call aborted`（v6 实测），也可能让工具的结构化返回先行（v7 的内部 race 先赢）——断言按双形态兼容；无论哪种形态，refix 内部状态机复位与审计落册均有保证。
2. **取消 × 失败学习的交互**：取消的修复按 failed 写回知识库 → 同指纹复发转人工——行为正确（诚实学习），测试已按此断言。
